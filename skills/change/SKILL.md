# change

수정 하나가 어느 문서층까지 퍼지는지 사용자가 말해 주지 않아도 찾아낸다. 하네스 공통 규칙은 하네스 `rules.md`를 따른다.

문서층:
- `roadmap.md` — 영역의 이름 · 의도 한 줄 · 순서 · 범위 밖. 상세는 쓰지 않는다.
- `specs/NNN-영역/spec.md` — 시작한 영역의 현재 진실. 쓰고 고치는 일은 `living-spec` update.
- `backlog.md` — 아직 spec이 없는 영역에 미리 적어 두는 상세(결정 · 파급 메모). 그 영역을 시작할 때 `flow`가 입력으로 쓰고 지운다.
- 디자인 스펙 — 값 · 부품 · 용도 · 화면 패턴.

## 1. 읽기
`roadmap.md` · `backlog.md` · 요청이 닿는 영역의 `spec.md` · `contracts/` · 그 영역을 쓰는 뒤 영역(spec이 있으면 `spec.md`, 없으면 roadmap 행과 backlog 항목) · 화면이면 `specs/design-system.md`.

## 2. 영향 판정
요청을 아래 표에 대어 바뀌는 문서를 모두 찾는다. 한 요청이 여러 줄에 걸칠 수 있다.

| 무엇이 바뀌나 | 고칠 문서 |
|---|---|
| 영역 추가 · 삭제 · 합침 · 나눔 · 순서 · 이름 · 의도 · 범위 밖 · 비전 · 용어 | `roadmap.md` (폴더 번호가 바뀌면 4의 "번호 다시 매김") |
| spec 있는 영역의 요구사항 · 화면 | 그 `spec.md`. roadmap은 의도 한 줄이 더는 맞지 않을 때만 |
| spec 없는 영역의 요구사항 | 의도 한 줄이 바뀌면 roadmap, 상세는 backlog의 그 영역 항목 |
| 다른 영역에 퍼짐 — 그 영역 spec 있음 | 그 영역 spec도 같은 변경에서 |
| 다른 영역에 퍼짐 — 그 영역 spec 없음 | backlog에 그 영역 항목 |
| 디자인 값 · 부품 · 배치 | 문서를 직접 고치지 않는다. 화면 항목은 spec `## 화면`에 쓰고, 디자인 스펙은 `flow` 2단계(새 용도는 `mockup`, 기존 화면은 `design-consistency` change)가 게이트②를 거쳐 고친다 |
| 문서는 맞고 코드만 다름 (버그) | 문서 없음 → 5의 버그 경로 |
| 요청한 것이 이미 문서에 있음 | 문서 없음. 어디에 있는지(FR · 줄) 알리고 진짜 뜻을 묻는다 |

퍼짐 찾기: 바뀌는 영역의 계약(`contracts/` · `data-model.md` · 화면 · 용어)을 roadmap의 뒤 영역 의도와 backlog 항목에 대어 본다.

의도 한 줄 · 비전 · 용어를 고치는 기준: 바뀐 뒤 그 줄을 글자 그대로 읽으면 틀린 말이 될 때만. 더 넓게 읽어서 덮이면 그대로 둔다.

이미 정한 결정과 부딪힘: 요청이 spec의 FR · roadmap · backlog에 적힌 결정과 어긋나면 그 결정(파일 · 줄)을 보이고 3에서 어느 쪽인지 묻는다. 새 결정을 따르면 옛 줄은 같은 변경에서 지우거나 고쳐 쓴다. 두 결정을 함께 남기지 않는다.

## 3. 영향 보고 · 확인
- 문서가 바뀌면: 바뀔 문서 · 파급 영역 · backlog에 적을 줄을 5~10줄로 보이고 AskUserQuestion으로 확인받는다.
- 묻는 것은 요청의 뜻과 부딪힌 결정 중 어느 쪽인지뿐이다. 어느 문서를 고칠지는 이 스킬이 판정한다("roadmap도 고칠까요?"라고 묻지 않는다). 뜻이 여럿이면 갈래마다 바뀔 문서를 붙여 보인다.
- 버그면: "문서 영향 없음 — 버그로 고침" 한 줄만 알리고 바로 5로 간다(게이트 없음).

## 4. 적용
- spec 있는 영역 · 새 영역: spec은 `living-spec` update가 쓰고 고친다. 새 영역이면 roadmap에 행을 먼저 넣는다.
- **backlog 항목:** 기존 backlog 모양을 따른다.
  ```markdown
  ## <묶음> — NNN에서 할 일 (YYYY-MM-DD, <무엇을 바꿔서>)
  - …
  ```
  같은 영역 항목이 이미 있으면 그 아래에 더하고, 줄 머리에 `(YYYY-MM-DD)`를 단다. 상세만 적고 spec처럼 깊게 쓰지 않는다.
- **번호 다시 매김:** 폴더 이름을 바꾸고 roadmap(영역 지도 · 작업 순서) · 모든 spec · backlog · `.specify/feature.json`의 폴더 참조를 함께 바꾼다. `FR-001` · `SC-001` 같은 요구사항 ID는 건드리지 않는다. 끝나면 옛 폴더 이름을 grep으로 찾아 0건(git 이력 · wiki 제외)인지 확인한다.

## 5. 다음 경로
- **spec이 바뀜 · 새 영역** → `flow`(게이트①부터).
- **roadmap · backlog만 바뀜** → `llm-wiki` → `docs(roadmap): …` 커밋.
- **버그** → 범용 디버깅 스킬이 있으면 그것으로 원인을 찾는다 → 재현 테스트를 먼저 쓰고 실패 확인(`tdd` B) → 고침 → `tdd` C 전체 테스트(화면이면 `tdd` D) → `fix(NNN-영역): …` 커밋. 고치다가 spec이 틀렸거나 비어 있음이 드러나면 멈추고 2로 돌아간다.

## 하지 않는 것
- 뒤 영역의 spec을 미리 쓰지 않는다. backlog에만 적는다.
- roadmap에 요구사항 · 기술 · 상세를 쓰지 않는다.
- spec에 기술 스택이나 디자인 값을 쓰지 않는다.
- spec을 직접 고치지 않는다. 고칠 때는 `living-spec` update의 진실 규칙을 따른다.
