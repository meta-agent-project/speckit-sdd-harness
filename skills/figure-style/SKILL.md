# 생성형 그림 화풍

사용자가 확정한 두 견본을 매번 실제 이미지로 전달해 강의·책 그림의 화풍을 맞춘다. 색을 자유롭게 사용했을 때 넓은 다색 면이 설명보다 눈에 띄었기 때문에, 그림 본체는 흑백으로 두고 색은 구조를 구분하는 데 쓴다. 장면·비유·구도는 내용에 맞게 선택한다.

## 생성할 때

1. [화풍 지침](references/style.md)과 [명세](references/spec.md)를 읽고, 다음 두 PNG를 순서대로 확인한다.
   - [구조 설명 견본](assets/structure.png): 흑백 그림에 색 테두리·이름표로 포함 관계를 설명한다.
   - [장면 설명 견본](assets/assembly.png): 검정 펜과 회색 명암, 가벼운 입체감과 사물 배치로 개념을 설명한다.
2. 원고에서 핵심 개념·관계·방향·이름표를 추려 한 번 준비한다. 이 준비에서 장 수와 장마다 부분·순서·최종 생성 요청을 함께 정한다. 단일 이미지 요청은 한 장이다. 카페·손·조립이라는 소재나 견본 배치를 그대로 복사하지 않는다. 명시적 찾기 요청·찾기 칸이 있을 때만 내용 참고를 검색한다.
3. 이미지 생성 도구의 참고 이미지 입력에 **두 PNG를 실제로 첨부**한다. 파일 이름이나 화풍 설명만 적는 것으로 대신하지 않는다. 검색한 내용 참고가 있으면 세 번째로 보내고, 첫 두 장은 화풍·세 번째는 내용 자료라고 구분한다.
4. 화풍 지침은 최종 생성 요청에도 넣는다. 명시적인 사용자 수정 요청은 기본 화풍보다 먼저 따른다. 요청 작성 AI와 이미지 생성 AI를 나누어 쓰면 양쪽에 두 PNG를 전달한다.
5. 생성 결과 PNG를 보존한 뒤 직접 열어 내용·관계·수치·필수 철자와 읽기 어려운 겹침·잘림을 확인한다. 이런 핵심 오류가 있을 때만 준비한 요청에 위치·수정 방향을 더하여 같은 두 견본으로 한 번 다시 만든다. 요청 쓰기를 다시 호출하지 않는다. 색·장식·여백의 취향 차이는 경고로 알리고 핵심 오류와 구별한다. 여러 강조색의 개수로 탈락시키지 않는다. 마지막 미통과를 통과로 표시하지 않는다. 점검 불가에서는 PNG를 남기고 불가 이유를 알린다.

이미지 생성 도구나 참고 이미지 전달 기능을 사용할 수 없으면 그 제한을 알린다. 기존 승인 이미지의 일괄 교체는 요청받은 범위에서만 한다.

## 앱과 함께 유지할 때

강의프로그램 앱은 `skill.figure-style`을 하네스의 **생성형 그림 화풍**으로 등록한다. 앱 하네스의 기본 글과 이 스킬의 `references/style.md`, 양쪽 PNG는 같은 승인본이다. 화풍을 바꾸라는 요청이 있으면 양쪽 지침·명세·견본을 함께 맞춘다. 앱의 그림 작업은 시작할 때 읽은 지침을 요청 작성·생성·검수까지 유지하고, 고친 지침은 다음 작업부터 사용한다.

## 실행 결과 예시와 점검 복구

- 앱의 새 실행 결과 자리는 위와 같은 생성형 경로를 기본으로 쓰고 `생성형 예시 · 실제 실행 안 함`을 표시한다. 예제 코드·패키지 설치·DB·개발 서버를 실행하지 않는다. 도구·설치·설정 화면은 비워 두며 실제 사진은 사용자가 기존 이미지 변경으로 넣는다.
- 준비 결과는 원고·블록·앞뒤 글·이름표·사용자 요청·화풍·참고 등 외부 입력 지문이 같을 때만 재사용한다. 지난 생성 요청/점검은 새 준비 때만 제공하는 내부 결과이며 캐시를 무효화하지 않는다.
- 앱은 이미지별 pending·passed·needsCorrection·unavailable과 경고·시각을 저장한다. 재시작은 저장 pending을 그대로 보존하고 확인 전으로 복구하여 점검만 재시도할 수 있다. checker만 무출력90초·전체180초다. 시간초과·전송오류·잘못된 답은 이미지 보존·점검 불가·다음 자리 진행이며 재생성 이유가 아니다.
- [점검 다시 시도]는 저장 PNG만 점검한다. 준비·검색·생성·품질 재생성을 하지 않는다. 기존 승인·수동 이미지를 자동 교체하지 않는다.
- 생성 원본 PNG의 바이트·색·흰 바탕·비율을 유지한다. 미리보기 프레임을 생성 비율 제약으로 쓰지 않는다.
