# flow-all

사용자는 spec 과 화면 시안만 승인한다.
그 뒤는 메인이 지휘하고 서브에이전트가 끝까지 만든다.
단계와 끝남 판정은 flow 를 따른다. 이 스킬은 여러 영역을 함께 돌리는 방법과 게이트 위치만 바꾼다.

## 시작

- constitution, roadmap, 프로젝트 CLAUDE.md 를 읽는다
- 동시 수, 모델 역할, 자원 규칙, 합치기 · 배포 규칙은 프로젝트 CLAUDE.md 를 따른다. 없으면 동시 3개다
- roadmap 영역마다 flow 의 진행 상태 표로 지금 단계를 판정한다
- 영역 · 단계 · 다음 일 표를 보이고, 몇 영역을 돌리고 몇 영역이 승인을 기다리는지 한 줄로 알린다

## 두 갈래

| 갈래 | 대상 | 하는 일 |
|---|---|---|
| 승인 갈래 | spec 이 없거나 승인 전인 영역, 화면이 있는데 디자인 승인 기록이 없는 영역 | flow 1 · 2 를 사용자와 한다 |
| 자동 갈래 | spec 이 승인됐고 화면이 있으면 디자인 승인 기록도 있는 영역 | flow 3 ~ 8 을 묻지 않고 한다 |

## 승인 갈래

- spec 초안은 영역마다 서브에이전트가 동시에 쓰고 메인이 읽고 고친다
- 화면이 있는 영역은 mockup 시안도 이때 만든다. 게이트 ① 과 ② 를 한 물음으로 받는다
- 승인 물음은 모아서 한다. 영역마다 요약 5~10줄과 열린 질문의 추천 답을 붙인다
- 승인되면 spec 상태 · 디자인 스펙 · 승인 기록을 고치고 그 영역을 자동 갈래로 넘긴다

## 자동 갈래

flow 3 ~ 8 의 규칙은 그대로다. 한국어 문서, tdd A ~ D, converge, 기준을 느슨하게 하지 않기를 지킨다. 묻지 않는 것만 다르다.

- 순서는 roadmap 작업 순서다. 앞 영역의 계약(contracts · data-model)이 필요한 일은 그 계약이 plan 에 있으면 시작한다
- 앞 영역 코드가 master 에 있어야 하는 구현은 그 영역이 합쳐질 때까지 기다린다
- 문서 단계(plan · tasks · analyze)는 같은 작업 폴더에서 돌린다. Spec Kit 명령마다 SPECIFY_FEATURE_DIRECTORY=specs/<폴더> 를 붙이고 .specify/feature.json 은 믿지 않는다
- 기존 영역의 tasks 를 다시 만들기 전에 커밋한다(flow 4)
- 구현은 영역마다 따로 worktree 에서 한다. 갈래 이름은 영역 폴더 이름이다
- 영역의 tdd C · D 와 converge 가 통과하면 합치기 담당이 master 에 합치고 전체 테스트를 다시 돌린다. 실패하면 그 영역 구현 에이전트에게 돌려보낸다
- 측정은 한 번에 하나만 돈다
- 메인은 지시문을 쓰고 결과 보고와 검증 출력을 직접 확인한다. 지시문에는 영역 폴더, 할 일 번호, 끝 기준, 자원 규칙을 넣는다
- plan 의 기술 결정은 묻지 않고 영역 끝 보고에 적는다

## 멈추는 때

그 영역만 멈추고 사용자에게 묻는다. 다른 영역은 계속 돈다.

- 테스트 · 자리 표 기준을 지킬 수 없을 때. 이유와 캡처를 붙인다
- spec 과 다른 결정이 필요할 때. living-spec update 로 고치고 그 영역은 승인 갈래로 돌아간다
- 같은 실패를 세 번 고쳐도 안 될 때
- 되돌리기 어렵거나 밖으로 나가는 일 중 프로젝트 규칙이 허락하지 않은 것

## 보고

- 영역 하나가 끝날 때마다 무엇을 했는지, 시험 결과, 남은 위험을 세 줄로 알린다
- 사용자가 물으면 영역 표를 다시 보인다
- 상태는 파일(spec 상태 · plan · tasks 체크 · roadmap · git)에서 읽는다. 따로 기록하지 않아서 새 대화에서도 flow-all 로 이어 간다

## 하지 않는 것

- spec 승인과 시안 고르기를 추측하지 않는다
- 자동 갈래에서 승인을 묻지 않는다
- 동시 수를 넘기지 않는다
